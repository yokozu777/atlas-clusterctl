# Что имеет смысл сделать и зачем

Сейчас у нас хороший внутренний инструмент «поднять и вести стенды».
Чтобы им удобно пользоваться самим и когда-нибудь спокойно выложить наружу —
не нужны десятки новых команд. Нужно чуть навести порядок и закрыть несколько дыр.

---

## 1. Упростить то, что путает

**Сделать**

- Оставить один способ синхронизировать репозитории с ролями (сейчас по сути
  два имени одной вещи).
- Сделать один канонический способ запускать кусок плана (`run --phases …`),
  остальное не рекламировать.
- Убрать из публичного дерева внутренние Jenkins-файлы, личные SSH-ключи и
  «свой» Docker-образ как дефолт.
- Внутренние отчёты (эта папка `notes/`) не смешивать с операторскими `docs/`.

**Что даст**  
Меньше «а как правильно?», меньше стыда при публикации, проще онбординг
нового человека.

---

## 2. Зафиксировать версии стека

**Сделать**  
В шаблонах и в проверках явно писать: какая версия `clusterctl` с какими тегами
sibling-репо работает. Не вечный `main` «как получится».

**Что даст**  
После обновления одной роли не разваливается весь кластер «молча». Можно
сказать: «вот этот набор — рабочий».

---

## 3. Одна команда «всё ли готово к запуску»

**Сделать**  
Короткий `doctor` / preflight: Python, Ansible, Docker (если нужен), есть ли
клоны ролей, не торчат ли `CHANGEME`, жив ли workspace.

**Что даст**  
Вместо часа отладки — сразу видно, чего не хватает до `run`.

---

## 4. Тестировать переменные без Proxmox

**Сделать**  
Набор готовых YAML-профилей (минимум / полный / заведомо битый) и автопроверки:
«эти переменные должны пройти / должны упасть».

**Что даст**  
Ловите 80% ошибок конфигурации за секунды в CI, а не после создания ВМ.
Куча переменных перестаёт быть лотереей.

---

## 5. Не выкладывать всё сразу

**Сделать**  
Снаружи сначала «ядро»: контроллер + provision + подготовка нод + infra-edge
(+ при желании k8s). PostgreSQL / Redis / Kafka / толстые addons — как
отдельные линии или beta.

**Что даст**  
Меньше поддержки, честнее качество. Не обещаете десятки ролей addons, если
их почти не покрывают тесты.

---

## 6. В больших стеках — профили, а не «всё включено»

**Сделать**  
В infra и k8s-addons явно: DNS / CA / registry, observability / storage /
identity — включаешь нужное, а не весь комбайн.

**Что даст**  
Проще понять продукт, проще тестировать, меньше сюрпризов на лабе.

---

## 7. Перед GitHub — техническая гигиена

**Сделать**  
Чистая история (или orphan), зелёный CI у clusterctl, нормальные
LICENSE / SECURITY / CONTRIBUTING, без внутренних имён в сообщениях об ошибках.

**Что даст**  
Можно спокойно открыть репозитории. Scrub рабочего дерева уже неплох, но
«как enterprise на GitHub» ещё рано.

---

## Чего не стоит делать сейчас

- Molecule, которая сама поднимает ВМ в Proxmox на каждый PR — дорого и хрупко.
- Ещё куча новых CLI-команд «на всякий случай».
- Пытаться идеально протестировать все addons сразу.

Живые прогоны на Proxmox оставить редкими (ночная lab / руками), а ежедневную
уверенность давать проверками переменных и плана.

---

## Если совсем коротко

| Сделать | Получите |
|--------|----------|
| Убрать дубли и внутренний мусор | Проще пользоваться и публиковать |
| Закрепить версии репо | Предсказуемые обновления |
| Doctor + проверки переменных | Быстрее находить ошибки до ВМ |
| Сначала ядро, профили в больших стеках | Реалистичный продукт, а не комбайн |
| Чистый git + зелёный CI | Нормальный выход на GitHub |

**Итого:** не «добавить ещё Ansible», а сделать то, что есть, понятным,
версионируемым и проверяемым — от этого пользы больше, чем от новых фич.
